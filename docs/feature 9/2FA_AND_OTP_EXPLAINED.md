# Feature 9: Two-Factor Authentication (2FA) & OTP Tokens

This document explains the technical concepts behind our **Feature 9 (2FA)** implementation and why specific components like **OTP Tokens** are crucial for security.

## 1. What is Two-Factor Authentication (2FA)?
2FA adds a second layer of security to your account. Instead of just entering a password ("something you know"), you must also provide a code generated by a device you possess ("something you have").

### Why Use It?
*   **Prevent Unauthorized Access:** Even if a hacker steals your password, they cannot access your account without your phone.
*   **Industry Standard:** Essential for applications storing sensitive data like passwords.

---

## 2. How Our 2FA Works (TOTP)
We use **Time-based One-Time Passwords (TOTP)**, the standard used by apps like **Google Authenticator**.

### Key Concepts:
1.  **Shared Secret:** When you enable 2FA, the server generates a unique **Secret Key** (e.g., `JBSWY3DPEHPK3PXP`). This key is stored securely in our database (`TwoFactorAuth` table) and shared with your phone via a **QR Code**.
2.  **Time Sync:** Both the server and your phone use the current time to generate a 6-digit code.
3.  **Validity Window:** The code changes every 30 seconds. The server accepts the current code (and usually the one immediately before/after to account for clock drift).

### The Flow:
1.  **Login:** server validates your `username` + `password`.
2.  **Check:** server sees `is2faEnabled = true`.
3.  **Challenge:** server pauses login and asks for the 6-digit code.
4.  **Verification:** You open your app, get the code, and send it to `/api/auth/verify-otp`.
5.  **Access:** If the code matches the secret key + time, the server issues your access token.

---

## 3. The Role of `OtpToken` (Server-Generated OTPs)
You might wonder: *If we have Google Authenticator, why did we also create an `OtpToken` entity?*

**They serve different purposes.**

### A. TOTP (Google Authenticator)
*   **Generator:** The user's phone app.
*   **Purpose:** Continuous authentication (Login).
*   **Dependence:** User *must* have their phone set up previously.

### B. `OtpToken` (Our Custom Entity)
*   **Generator:** The **Server**.
*   **Purpose:** Transactional / Event-based verification.
*   **Use Cases:**
    *   **Email Verification:** Sending a code to verify a new email address.
    *   **Password Reset:** Sending a code to allow a password change.
    *   **Sensitive Access (Feature 15.5):** If a user needs to view a highly sensitive password, we might require an *additional* email code or a specific server-generated token, separate from their standard 2FA.
    *   **Backup/Recovery:** Can be used to implement temporary access tokens.

### How `OtpToken` Works:
1.  **Generation:** Server creates a secure random code (e.g., `849201`).
2.  **Storage:** Saved to `OtpToken` table with an `expiryDate` (e.g., 15 minutes) and `isUsed = false`.
3.  **Delivery:** Sent to user (Email/SMS).
4.  **Validation:** User enters code -> Server checks DB -> Marks `isUsed = true`.

---

## Summary
*   **Feature 9** implements **TOTP 2FA** for secure login.
*   We added **`OtpToken`** infrastructure to support future features like **Email Verification** and **Highly Sensitive Data Access**, ensuring our security architecture is robust and flexible.
